# Data Flow & Side-Effect Map

**Purpose:** Maps how entities mutate and propagate throughout the system. AI agents must consult this document to ensure they do not orphan data, leak spoilers, or bypass necessary side-effects.

## 1. Primary Request & Mutation Data Flow
1. **Client (Hotwire Web or Flutter `/api/v1`)** submits request payload (Cookie session or `Authorization: Bearer <raw_token>`).
2. **Authentication Layer** resolves `Current.user` (via `Session` cookie or SHA-256 `ApiToken.find_by(token_digest: ...)`), verifying `user.discarded_at.nil?`.
3. **Authorization Layer (Pundit)** executes policy check (`authorize`), enforcing the **"Block Wins"** law first before evaluating friendship, `WishlistShare`, or `share_token` access.
4. **Domain Service Object** executes business logic within a PostgreSQL transaction (checking preconditions, database uniqueness constraints, and postconditions) and writes an immutable `AuditEvent` when applicable.
5. **Notification Dispatcher (Solid Queue)** asynchronously enqueues localized (`user.locale`) in-app, email, and push notifications after transaction commit.

## 2. Cascading Side Effects

| Trigger Action | Required Side Effect | Mechanism |
|---|---|---|
| **User A blocks User B** (`REQ-BLOCK-002`) | 1. Destroy any `Friendship` (accepted or pending) between A and B.<br>2. Delete all `WishlistShare` records between A and B.<br>3. Cancel any active/grace `Reservation` held by A on B's items or by B on A's items (silently, no notification).<br>4. Record `AuditEvent`. | Synchronous DB Transaction (`UserBlock.block!` + `:destroy_friendships` hook) |
| **User accepts or removes a `Friendship`** (`REQ-SOC-001`, `REQ-ADM-001`, `REQ-BLOCK-002` parity) | 1. On acceptance (`Friendship#accept!`): transition `status` to `"accepted"` and record immutable `AuditEvent` (`"friendship.accepted"`).<br>2. On decline/cancel/unfriend (`Friendship#remove!`): delete `WishlistShare` rows between the pair, record immutable `AuditEvent` (`"friendship.removed"`), and destroy the `Friendship` record. | Synchronous DB Transaction |
| **User submits an abuse `Report`** (`REQ-SOC-001`, `REQ-DISC-001`, `REQ-ADM-001`) | 1. Validate `ReportReason` Value Object and verify no duplicate `"pending"` report exists for `(reporter_id, reportable_type, reportable_id)`.<br>2. Persist `Report` (`status: "pending"`) and record immutable `AuditEvent` (`"report.created"`). | Synchronous DB Transaction (`Report.submit!`) |
| **User changes `@username`** (`REQ-USER-001`, `REQ-USER-004`) | 1. Verify `username_changed_at` is `nil` or `<= 30.days.ago`.<br>2. Quarantine old `@username` for 30 days (`UsernameReservation`).<br>3. Update `username` and `username_changed_at`. | Synchronous DB Transaction (`UsernameChangeService`) |
| **User logs out of `/api/v1` or revokes `ApiToken`** (`REQ-NOTIF-002`) | 1. Mark `ApiToken` revoked/deleted.<br>2. Immediately delete/deactivate any FCM `DeviceToken` bound to that `api_token_id` to prevent push spoilers on shared devices. | Synchronous DB Transaction |
| **User soft-deletes account** (`REQ-LIFE-002`) | 1. Set `discarded_at = Time.current` on `User` and cascade soft-delete kept owned `Wishlists`, which in turn cascade soft-delete kept `Items` via SoftDeletable hooks (`REQ-LIFE-001`).<br>2. Persist cascaded wishlist IDs on the `user.soft_deleted` `AuditEvent` metadata (`cascaded_wishlist_ids`) so restore cannot revive earlier intentional wishlist deletes.<br>3. Revoke all active `Sessions`, `ApiTokens`, and `DeviceTokens`.<br>4. Cancel all active/grace reservations **held by** the user (`Reservation.cancel_for_reserver!`); item soft-delete cascade cancels holds **on** owned items.<br>5. Schedule 30-day PII purge check via Solid Queue. | Synchronous DB Transaction + Solid Queue Scheduled Job |
| **Owner pastes store URL for item preview** (`REQ-ITEM-006`) | 1. `POST /api/v1/link_previews` fetches `og:title` / `og:image` with SSRF protections (timeouts, redirects capped, private/link-local/metadata IPs blocked).<br>2. Client shows preview; nothing is persisted until the owner confirms.<br>3. On confirm, create/update sends `confirmed_preview`; server re-validates the image URL and may attach a processed WebP via ActiveStorage. | Synchronous HTTP + best-effort extract; persist only on confirm |
| **User restores account within grace** (`REQ-LIFE-002`) | 1. Clear `User.discarded_at` within SoftDeletable 30-day window.<br>2. Restore only wishlists whose IDs appear in the latest `user.soft_deleted` AuditEvent `cascaded_wishlist_ids` metadata (intentional pre-delete soft-deletes stay discarded).<br>3. Issue a fresh API token on the restore endpoint. | Synchronous DB Transaction |
| **Wishlist switched to `friends`-only (private)** (`REQ-WISH-002`) | 1. Set `share_token = nil` (invalidating any previously shared Secret Link).<br>2. Revoke secret-link-derived `WishlistShare` access. | Synchronous Model/Service Hook |
| **Wishlist or Item soft-deleted** (`REQ-LIFE-001`, `REQ-RES-003`) | 1. Set `discarded_at` on `Wishlist` and its `Items`.<br>2. Transition any active/grace `Reservation` on affected items to `canceled` (ensuring zero ghost reservations if restored later).<br>3. Notify the pre-cancel reserver via `NotificationDispatcher` (`reservation.item_deleted`). | Synchronous DB Transaction + `NotificationDispatcher` |
| **Wishlist restored from soft-delete** (`REQ-LIFE-001`) | 1. Clear `discarded_at` on `Wishlist` and its `Items`.<br>2. Do **not** restore previously canceled reservations (items return clean). | Synchronous DB Transaction |
| **Owner edits critical fields (`title`, `specifications`, `links`) of an Item with an active reservation** (`REQ-RES-003`) | 1. Persist item changes.<br>2. Notify the active reserver via `NotificationDispatcher` (`reservation.item_critical_edit`). | After-commit / controller hook → `NotificationDispatcher` |
| **Image uploaded to `Item`** (`REQ-ITEM-002`) | 1. Validate <= 2MB and max 3 images.<br>2. Resize to <= 1600px longest side, re-encode to WebP, and **strip all EXIF/GPS metadata** via `libvips`. | ActiveStorage / `libvips` Image Processing Pipeline |
| **Item reserved (Sprint 5) or secretly purchased (Sprint 6)** (`REQ-RES-001`, `REQ-RES-002`, `REQ-GIFT-002`) | 1. Insert/update `Reservation` (`active` in S5; gift statuses in S6).<br>2. **MUST NOT** update `items.updated_at` (no side-channel timestamp leak to owner).<br>3. Record `AuditEvent`.<br>4. Non-owner clients read viewer-relative `availability` (`available` \| `reserved_by_me` \| `unavailable`). | Synchronous DB Transaction (`ReservationService`) |
| **Logged-in Secret Link sharee reserves / extends / cancels** (`REQ-WISH-002`, O4B) | Same domain transitions as `/api/v1` reservations, via Hotwire `SecretLinkReservationsController` on `/s/:share_token`. Guests are redirected to login with `return_to`. | Synchronous Web request + `ReservationService` |
| **Reservation `estimated_date` elapses in reserver's `time_zone`** (`REQ-RES-006`, O7A) | 1. Transition status from `active` to `expired_grace` (`grace_expires_at` ≈ now + 72h in reserver zone).<br>2. Notify reserver (`reservation.grace_started`) — extend or cancel only in Sprint 5. | Solid Queue Recurring Job (`ReservationGraceSweepJob`) |
| **Reservation remains in `expired_grace` past `grace_expires_at`** (`REQ-RES-006`, O7A) | 1. Transition status from `expired_grace` to `auto_released` (frees partial unique index slot).<br>2. Notify reserver (`reservation.auto_released`). Discarded reservers cancel safely without aborting the batch. | Solid Queue Recurring Job (`ReservationGraceSweepJob`) |
| **Reserver marks item as `delivered_pending_confirmation`** (`REQ-GIFT-001`) | 1. Update gift/reservation status.<br>2. Send **anonymous** notification to wishlist owner (*"Someone marked [Item] as delivered! Confirm receipt?"*). | Synchronous DB Transaction + Solid Queue Notification Job |
| **Owner marks item as `received_confirmed` (1-step or confirming delivery)** (`REQ-GIFT-001`, `REQ-GIFT-003`, `REQ-GIFT-004`) | 1. Mark item as `received_confirmed` (moves to bottom *"Received Gifts"* section).<br>2. If an active reservation by a friend existed, close it (`completed_by_gift` or `canceled_by_owner_receipt`) and notify that friend.<br>3. If owner included an optional anonymous *"Thank You"* note, deliver it privately to the gifter without exposing the gifter's identity to the owner. | Synchronous DB Transaction + Solid Queue Notification Job |
| **Participant drops out after Secret Santa draw (`v1`)** (`REQ-ACT-003`, `REQ-ACT-004`) | If creator selects **Blind Auto-Bridge**:<br>1. Validate exclusion compatibility (`A -> C`).<br>2. Reassign `A` to gift `C` in DB without exposing `A` or `C` to the creator.<br>3. Notify `A` privately of their updated recipient. | Synchronous DB Transaction (`ActivityDropoutBridgeService`) + Solid Queue Notification Job |

## 3. Caching & Serializer Isolation Strategy
* **Strict Role-Based Serialization (Anti-Spoiler Boundary):**
  * **Owner Serializer View:** Never includes `availability` or reservation identity on item payloads. Gift confirmation states (`delivered_pending_confirmation` / `received_confirmed`) arrive in Sprint 6.
  * **Friend / Link Viewer Serializer View (O3A):** Exposes `availability`: `available` | `reserved_by_me` | `unavailable`. Full reservation details (`private_note`, `estimated_date`) are returned only on the reserver's own reservation resources (`POST/PATCH` response, `GET /my_reservations`), never to third parties or the owner.
  * **Admin Audit View (Web Only):** Exposes full `Reservation`, `GiftRecord`, online purchase link reference, and `AuditEvent` history.
